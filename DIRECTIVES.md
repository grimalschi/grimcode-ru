Этот файл написан человеком, и только им может редактироваться. Нейросеть не может и не должна вносить изменения в этот файл.
В этом файле хранятся директивы проекта — основные принципы и требования, закладываемые разработчиком проекта, чтобы нейросеть всегда могла к ним обратиться и принять решение в соответствии с ними.
Каждое правило из этого файла является директивой.
Если какие-либо задачи, которые агент делает по просьбе человека, противоречат директивам, агент должен сообщить об этом человеку, чтобы человек решил, нужно ли обновлять директивы, или менять задачу.

# Суть проекта
Владелец проекта должен описать здесь, что это за продукт, для кого он делается и какие основные задачи решает.

# Архитектура сервисов
Проект разделен на полностью независимые сервисы (services), которые не зависят друг от друга напрямую.
Каждый сервис — это отдельный докер контейнер. Проект сам по себе является композицией сервисов-контейнеров.
Каждый из них имеет или может иметь свою базу данных, но не работает напрямую с базами данных других сервисов.
Межсервисное взаимодействие осуществляется только с помощью внутреннего API, построенного через контракты (contracts) и oRPC.
Прямое взаимодействие сервисов вне этого API контрактов запрещено в целях сохранения архитектуры чистой и красивой.

## Границы сервисов
Сервисы не импортируют соседние services/*, только свою папку, contracts/, shared/. Межсервисно только HTTP/oRPC.
Каждый докер контейнер монтирует только свою папку, contracts и shared, если нужно.
Проверка нарушения границ обязательна после изменений в сервисах.

# Переменные окружения
Переменные окружения находятся в .env в корне проекта.
Локально .env создает bootstrap, после чего человек при необходимости меняет значения. При деплое значения задает человек, отвечающий за настройку платформы деплоя.
.env.example хранится в репозитории, а .env не хранится в Git.
Каждый сервис может запросить только те переменные, которые ему нужны и которые объявлены для него в docker-compose файле.

# Документация
Агенты должны поддерживать документацию проекта и каждого сервиса в хорошем актуальном состоянии.
Подробное и актуальное описание каждого сервиса должно храниться в README.md в папке этого сервиса.

# Порядок обработки запросов
Сервис gateway отвечает за вход, маршрутизацию и безопасность внешних запросов, но не содержит бизнес-логику приложения.
Все запросы /admin/service/:name/* идут в соответствующий сервис :name, с проверкой админской авторизации и права этого администратора на сервис.
Все запросы /admin/* идут в сервис admin с проверкой админской авторизации.
Все запросы /service/:name/* идут в соответствующий сервис без админской авторизации.
Все запросы /app/* идут в сервис app без админской авторизации на gateway. Сервис app сам проверяет обычную пользовательскую авторизацию там, где она нужна.
Все остальные запросы идут в сервис site.
Запросы проксируются без изменения адреса, то есть сервисы получают на вход запросы с теми адресами, которые получает gateway.
Безопасность /service/:name/* — ответственность самого сервиса.

# Безопасность админки
Сервис admin хранит список администраторов и их права.
При первом авторизованном открытии админки сервис admin проверяет список администраторов. Если он еще пуст, admin получает из auth самого первого зарегистрированного пользователя и создает для него роль владельца (owner).
Владельцем становится именно первый пользователь в auth, а не тот, кто первым открыл админку.
Список администраторов отделен от продуктовых профилей пользователей.
Администратор использует обычную identity и сессию из auth. Отдельной регистрации, паролей и сессий для администраторов нет.
Владелец имеет доступ ко всем сервисам в админке. Владелец может назначать других пользователей администраторами и выбирать, к каким сервисам у них есть доступ.
Обычный администратор видит в центральной админке только разрешенные ему сервисы.
Adminer доступен только владельцу. Обычному администратору доступ к Adminer выдать нельзя.
Gateway должен проверять право администратора на сервис для каждого запроса /admin/service/:name/*. Если права нет, запрос не должен попадать в сервис.
Скрытие сервиса в меню не является проверкой безопасности. Проверка всегда делается на gateway.
Некоторые сервисы доступны только админам и не имеют публичной части, как adminer.

# Пользователи
Сервис auth хранит минимальную идентичность пользователя и способы входа.
Он не знает продуктовый профиль пользователя, его настройки и права администратора.
Даже если таблица в auth называется users, это identity users, не продуктовый профиль.
Сервис users хранит данные, которые относятся к продуктовому профилю пользователя.
Сервис admin хранит права администратора и доступ к сервисам админки.

# Локальный запуск
В процессе разработки используются git worktrees. Bootstrap каждого worktree выбирает ему свободные порты, если нужно запустить проект локально.
Каждый worktree берет .env файл из основной локальной копии проекта как основу и заменяет в нем worktree-specific значения.
Запуск worktree bootstrap делается только через предусмотренный для этого скрипт.
Каждый worktree использует отдельный локальный PostgreSQL. При bootstrap базы данных копируются из основной локальной копии проекта. Повторное копирование, которое может затереть изменения в базе worktree, выполняется только явно.

# Поведение агентов
Агент должен уважать директивы и следить за тем, чтобы функционал проекта соответствовал директивам.
Агент должен уважать документацию и следить за тем, чтобы документация всегда была в актуальном состоянии.
Если агент запущен в worktree, то он запускает проект на отдельном свободном порту, если запуск нужен.
Перед тем как завершать работу и сообщать об этом человеку, агент должен самостоятельно перепроверить качество выполненной работы. Важно убедиться, что не оставлено хвостов, ничего не упущено и задача выполнена в полной мере.
Если задача изменяет runtime или пользовательский интерфейс, агент должен запустить проект на порту и прислать человеку ссылку, чтобы результат можно было сразу открыть.

# Почта
Шаблоны писем хранятся на своей стороне.
Текстовые версии писем генерируются автоматически на основе HTML-кода писем.
В логах отправки писем сохраняются HTML и текстовый вариант каждого письма, статусы отправки, доставки и информация, которую дает почтовый сервис.
