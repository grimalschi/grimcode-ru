# Архитектура проекта

Модульный монолит: один процесс, одна база PostgreSQL и самостоятельные модули в `modules/`. Каждый модуль владеет своей логикой, HTTP-интерфейсами, UI и данными. Верхний слой соединяет модули и запускает приложение.

## Композиция

Корневой [`index.ts`](index.ts) читает окружение, создаёт модули в порядке зависимостей, передаёт им настройки и API, применяет миграции и открывает HTTP-порт.

Фабрика `createModule({ env, modules })` получает настройки один раз. Проверка настроек и значения по умолчанию принадлежат модулю. В `modules` передаются готовые API ранее созданных зависимостей: потребитель вызывает, например, `modules.email.send(input)`.

Фабрика возвращает [ModuleInstance](contracts/README.md#module-instance) с нужными возможностями: `publicFetch`, `adminFetch`, `internalCaller`, описанием `admin` и `migrate`. Композиция собирает из экземпляров HTTP-обработчики и список административных экранов.

## Границы

Модуль импортирует свои файлы, внешние библиотеки и типы `@template/contracts`. Его зависимости от других модулей выражены через API, объявленные в контрактах один раз. Внутренние вызовы выполняются через tRPC caller в том же процессе.

Настройки приходят через фабрику; чтение окружения остаётся в композиции. ESLint проверяет границы импортов и прямые обращения к `process.env` и `import.meta.env`. Передачу настроек через фабрику проверяют в ревью. Внутреннюю реализацию модуль меняет самостоятельно, сохраняя свои контракты.

## Данные

Модуль с данными владеет схемой с именем своего `id`. Его пул использует переданный `DATABASE_URL` и устанавливает собственный `search_path`. Метод `migrate()` создаёт схему и применяет [миграции модуля](docs/development.md#migrations); приложение начинает принимать запросы после их успешного завершения.

Данные другого модуля доступны через его API. Прямые обращения к чужим таблицам и межмодульные SQL-зависимости запрещены. Это правило проверяют в ревью: общая учётная запись PostgreSQL технически имеет доступ ко всем схемам. Исключение — инструмент владельца для работы с данными в Admin.

## HTTP и доступ

[Router](modules/router/README.md) — единственный внешний HTTP-вход. Он получает внутренние API через `modules`, HTTP-обработчики — через `publicFetches` и `adminFetches`, и передаёт запросы с исходными адресами. Публичный и административный входы модуль строит отдельно.

Router проверяет каждый административный запрос через [Admin](modules/admin/README.md) и передаёт подтверждённый `adminContext` вторым аргументом `adminFetch`. В Hono настройки модуля и контекст запроса доступны через [Bindings](contracts/README.md#http-context). Admin хранит роли и права, собирает панель из экранов модулей и проверяет операции владельца в своём API. За пользовательскую авторизацию отвечает модуль, принимающий публичный запрос.

Identity и сессии принадлежат [Auth](modules/auth/README.md), продуктовые профили — [Users](modules/users/README.md), права администраторов — Admin. Администраторы используют сессии Auth. [Web](modules/web/README.md) объединяет публичные страницы с SSR и пользовательский интерфейс `/app/`, который выполняется в браузере.
