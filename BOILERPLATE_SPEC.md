# Техническое задание на универсальный шаблон проекта

Статус: draft, обновлён после двух сравнительных прогонов и шести reference-aligned реализаций
Результат: один готовый repository template без генераторов и вариантов комплектации

## 1. Цель

Создать нейтральный шаблон веб-проекта с микросервисной архитектурой, единым публичным Gateway,
SSR-сайтом, пользовательским SPA-приложением, общей авторизацией, центральной админкой,
админками сервисов, уведомлениями, почтой и изолированными данными сервисов.

Шаблон копируется целиком. При создании проекта не выбираются модули, не запускается генератор и
не выполняется массовое переименование исходников. Новая предметная функциональность добавляется
после копирования как обычные новые сервисы или изменения существующих.

Это ТЗ описывает полный конечный repository template. Экспериментальные реализации используются
только как источник проверенных решений и найденных ошибок: ни одна из них не является кодовой
основой шаблона и не уменьшает его состав. Route probes, fixtures, макеты и временно пропущенные
сервисы не считаются реализацией требований этого документа.

## 2. Создание нового проекта

Новый проект создаётся через **Use this template**, fork или обычное копирование репозитория.

После копирования владелец:

1. описывает продукт в **DIRECTIVES.md**;
2. заменяет логотип, favicon, название и базовые цвета;
3. заполняет legal-страницы перед production;
4. задаёт production-домен и секреты на deployment platform.

Публичные метаданные и брендинг меняются в обычных файлах соответствующего приложения, а параметры
окружения задаются через env. Дополнительного слоя конфигурации для этого не вводится.

### 2.1. Основа шаблона

Шаблон реализуется как один стандартный standalone-проект непосредственно по этому ТЗ. Готовые
reference assets, уже включённые в repository, используются без повторной генерации.

Без повторного проектирования реализуются:

- pnpm workspaces и Turborepo;
- структура **services/**, **contracts/** и **shared/**;
- service-targeted Dockerfile и Docker Compose topology;
- отдельные service containers и service databases;
- HTTP/oRPC и Zod contracts;
- Gateway routing и proxy без переписывания path;
- central Admin shell, iframe composition и синхронизация URL/темы;
- Email lifecycle: templates, locales, versions, draft, publish, preview, test send, delivery и audit;
- внутренний Adminer container, его wrapper и полный stylesheet;
- shadcn/ui source components и общий non-React admin UI kit;
- проверки границ сервисов.

Намеренно меняются:

- проектные названия, домены, legal placeholders и предметно-специфические сервисы;
- Unlayer заменяется на self-hosted Maily;
- бинарный список администраторов заменяется на роли **owner/admin** и доступы к сервисам;
- Site переводится на TanStack Start, App и Admin — на TanStack Router;
- Email получает UniSender Go как единственный готовый production transport шаблона.

Прототипы, подменяющие отдельные containers одним Node-процессом с несколькими listeners, Unix
sockets, in-memory state, макетом Adminer или самописной имитацией shadcn, не являются основой
реализации.

## 3. Environment

**.env.example** хранится в Git и документирует все поддерживаемые переменные без реальных
секретов. **.env** игнорируется Git.

Основные параметры:

- **PROJECT_SLUG** задаёт техническое имя проекта и используется для Compose, cookie и имён БД;
- **GATEWAY_PORT** используется только локально;
- **POSTGRES_PORT** используется только для локального подключения к PostgreSQL с host-машины;
- **PUBLIC_SITE_URL** содержит внешний origin проекта;
- **DATABASE_URL** задаёт подключение к PostgreSQL;
- **EMAIL_PROVIDER** выбирает local log transport или UniSender Go.

При первом локальном bootstrap скрипт берёт **PROJECT_SLUG** из имени репозитория, выбирает
свободные **GATEWAY_PORT** и **POSTGRES_PORT** и сам записывает локальный **PUBLIC_SITE_URL** в
игнорируемый **.env**. Человек может изменить эти значения вручную.

В production **PUBLIC_SITE_URL** и секреты задаёт человек, отвечающий за deployment. Внешний домен
направляется платформой на фиксированный внутренний порт Gateway, поэтому **GATEWAY_PORT** в
production не заполняется.

### 3.1. Кто задаёт порты

| Порт | Local | Production |
| --- | --- | --- |
| Внутренние порты Gateway и сервисов | зафиксированы в Compose, человек их не задаёт | зафиксированы в образах и Compose |
| Host-порт Gateway | bootstrap выбирает автоматически; ручное значение — только override | отдельной env-переменной нет; платформа направляет домен на Gateway |
| Host-порт PostgreSQL | bootstrap выбирает автоматически; нужен только локальным инструментам | отсутствует |
| Порт production PostgreSQL | не используется | приходит от DB provider внутри **DATABASE_URL** |
| Порты Adminer и остальных сервисов | наружу не публикуются | наружу не публикуются |

Обычно человек не вводит номера портов вообще. Локально это делает bootstrap. В production человек
задаёт домен и **DATABASE_URL**; если deployment platform просит target port, выбирается уже
зафиксированный внутренний порт контейнера Gateway.

Локальные host-порты Gateway и PostgreSQL по умолчанию привязываются к **127.0.0.1**, а не ко всем
сетевым интерфейсам. Явно открыть их в локальную сеть можно только осознанным override.

Исходники, package names и Dockerfiles при смене проекта не изменяются. Отдельный обязательный
scope для private workspace packages не устанавливается: шаблон сохраняет свои нейтральные имена.

## 4. Состав шаблона

Шаблон всегда содержит все перечисленные части в рабочем, а не демонстрационном виде:

1. **gateway** — публичный вход, маршрутизация и внешняя безопасность;
2. **site** — публичный SSR-сайт;
3. **app** — пользовательское SPA-приложение;
4. **admin** — права администраторов и центральная админка;
5. **auth** — identity, способы входа и сессии;
6. **users** — продуктовый профиль пользователя;
7. **notifications** — приём и маршрутизация событий;
8. **email** — шаблоны и доставка писем;
9. **adminer** — owner-only интерфейс к локальным и разрешённым БД;
10. **contracts** — oRPC-контракты и Zod-схемы;
11. **shared** — общие технические utilities и UI-основа админок;
12. PostgreSQL и Docker Compose для локальной разработки.

## 5. Структура и границы

Runtime-код находится в **services/**, контракты — в **contracts/**, общие технические части — в
**shared/**, инфраструктура — в **docker/** и **scripts/**, документация — в **docs/**.

Runtime-сервис может импортировать только свою папку, **contracts/**, **shared/** и внешние пакеты.
Импорт соседнего сервиса запрещён. Межсервисное взаимодействие выполняется только через HTTP/oRPC
по контрактам. Сервис не читает и не изменяет БД другого сервиса.

В **shared/** не помещаются бизнес-логика и repositories конкретных сервисов.

У каждого сервиса есть README с подробным и актуальным описанием сервиса. Изменение архитектуры,
маршрутов, данных, env или контрактов сопровождается обновлением документации.

Workspace использует один package manager, один lockfile и согласованные версии React, TypeScript,
Vite и test tools. Сервисы не создают собственные независимые npm lockfiles.

Локальные команды сервиса после чистой установки должны либо автоматически собирать нужные
workspace dependencies, либо запускаться через корневой task graph. Ситуация, когда service
typecheck не находит ещё не собранные **contracts/** или **shared/**, не считается нормальным
готовым workflow.

В репозитории используется один общий service-targeted Dockerfile с аргументом сервиса, но из него
собирается отдельный production image для каждого сервиса. В image попадает только dependency
closure выбранного сервиса, как в текущем Dockerfile с workspace filter и production deploy. Общие
build stages и cache разрешены, но один общий runtime image для всех Node services не используется:
он копировал бы весь monorepo и сборки соседних сервисов в каждый container, увеличивал размер
образов и связывал их обновления.

Корневые проверки после clean install работают через зафиксированный в репозитории package manager.
Они не зависят от недокументированного глобального **pnpm** или временного wrapper вне репозитория.

## 6. Gateway и маршрутизация

Gateway — единственный публично доступный контейнер. Он не имеет БД и не содержит продуктовую
бизнес-логику.

| Входящий путь | Получатель | Проверка Gateway |
| --- | --- | --- |
| **/admin/service/:name/** | админка разрешённого сервиса | session, роль и доступ к сервису |
| **/admin/** | admin | session и наличие admin role |
| **/service/:name/** | сервис из public allowlist | безопасность endpoint обеспечивает сервис |
| **/app/** | app | App допускает только публичные auth routes, остальные проверяет по user session |
| всё остальное | site | публичный доступ |

Путь передаётся сервису без переписывания. Gateway использует явные public и admin allowlists;
значение **:name** никогда напрямую не превращается в hostname контейнера.

Сервисы обращаются друг к другу напрямую по внутренней Docker-сети. Процедуры, не предназначенные
для браузера, Gateway наружу не публикует.

После успешной admin-проверки Gateway передаёт целевому сервису проверенный контекст
администратора и request id. Это нужно целевому сервису для owner-only операций и audit без
повторной проверки сессии. Перед проксированием Gateway удаляет одноимённые заголовки клиента,
чтобы браузер не мог подделать этот контекст.

Базовая trust boundary остаётся простой:

- только Gateway публикуется наружу;
- остальные сервисы доступны только во внутренней Docker-сети;
- Gateway удаляет все входные control headers администратора;
- после разрешения Admin Gateway создаёт заново user id, email, role и request id;
- HMAC, JWT, mTLS и отдельная ротация ключей для этого контекста в стандартный шаблон не входят.

Все запросы под **/admin/**, включая HTML, API и assets, проходят одинаковую admin-проверку.
Отдельная публичная политика для admin assets заранее не вводится.

Gateway не запрашивает у upstream сжатое тело, если используемый proxy runtime сам декодирует
ответ. После декодирования он не пересылает устаревшие **content-encoding** и **content-length**.
Это обязательно проверяется на реальном сжатом asset, а не только на HTML.

Явные service ids в Gateway allowlist и Admin shell должны быть согласованы автоматическим тестом.
Отдельный **project.config.ts**, runtime service discovery или пользовательский конструктор модулей
не вводятся.

## 7. Админка и права

### 7.1. Модель

Auth хранит общую identity и session. Admin отдельно хранит реестр администраторов, их роли,
доступ к сервисам и audit изменений. Отдельной admin-регистрации, паролей и сессий нет.

Роли:

- **owner** — видит все admin services и управляет администраторами;
- **admin** — видит только явно разрешённые ему сервисы.

Adminer всегда доступен только owner и не может быть выдан обычному admin.

### 7.2. Первый owner

При первом авторизованном открытии **/admin** Admin проверяет свой реестр. Если он пуст, Admin через
Auth contract получает самого первого зарегистрированного пользователя и атомарно назначает его
owner.

Owner определяется порядком регистрации в Auth, а не тем, кто первым открыл админку. Если её
открыл другой пользователь, owner всё равно становится первый пользователь Auth, а текущий запрос
получает отказ. Bootstrap идемпотентен и прекращается после появления первого администратора.

### 7.3. Управление администраторами

В центральной админке есть owner-only экран со списком администраторов и их доступов. Продуктовый
список пользователей из Users здесь не показывается.

Owner добавляет уже зарегистрированного пользователя по email, включает или отключает его,
назначает роль и выдаёт доступ к сервисам. Нельзя отключить или понизить последнего owner. Все
изменения прав записываются в audit.

Администраторы не удаляются физически: используется отключение с сохранением истории. Owner может
изменить собственную роль или отключить себя только при наличии другого активного owner. Проверка
последнего owner выполняется транзакционно в Admin DB.

Owner-only mutations защищаются общей session security и CSRF-проверкой. Изменение прав начинает
действовать со следующего запроса через Gateway.

### 7.4. Проверка доступа

Вся проверка сведена к одному внутреннему методу Admin. На каждом admin-запросе Gateway передаёт в
него session cookie и, если запрашивается админка сервиса, имя этого сервиса.

Admin через Auth определяет текущего пользователя, читает собственные права и возвращает Gateway
либо отказ, либо проверенный user id и роль. Правило доступа простое:

- пользователя нет в Admin — отказ;
- owner — разрешены все admin services;
- admin — разрешены только явно выданные ему сервисы;
- Adminer — всегда только owner.

Gateway ничего не вычисляет сам, не хранит копию прав и не кэширует результат. При отказе он
возвращает 403, при разрешении проксирует запрос и передаёт сервису проверенный контекст
администратора. Поэтому изменение прав действует со следующего запроса.

Sidebar получает список сервисов из того же Admin service. Скрытие пункта меню является только
интерфейсом, а прямой URL проходит ту же проверку Gateway.

Если Auth или Admin недоступен, Gateway закрывает доступ и возвращает service-unavailable response,
а не маскирует инфраструктурную ошибку под отсутствие прав.

Bootstrap первого owner расширяет уже существующий PostgreSQL/oRPC flow:

1. Admin через Auth contract получает earliest registered identity с детерминированным порядком;
2. если Auth пуст, owner не создаётся и Admin возвращает состояние ожидания первого пользователя;
3. Admin выполняет идемпотентный insert owner в своей DB;
4. unique constraint не допускает двух bootstrap owners;
5. audit создаётся только запросом, который действительно вставил owner;
6. параллельные запросы завершаются с одним и тем же owner.

### 7.5. Интерфейс

Центральная админка использует **shadcn/ui**. Админки сервисов используют те же компоненты и design
tokens либо точно мимикрируют под центральную админку, если их технология не позволяет подключить
общий React UI.

Admin shell содержит sidebar сервисов, текущего администратора, logout и темы light, dark и
system. Админки сервисов открываются внутри shell и получают активную тему.

Logout выполняется server-side операцией Auth: сессия инвалидируется в Auth DB, после чего сервер
очищает HttpOnly cookie. Удаление cookie только через client JavaScript logout не реализует.

Для central React Admin в репозитории обязательно находятся настоящие shadcn source components:

- **components.json**;
- **components/ui/**;
- Radix primitives там, где они нужны компонентам;
- **class-variance-authority**, **clsx** и **tailwind-merge**;
- Tailwind и semantic CSS variables.

Одних похожих CSS tokens и самописных кнопок недостаточно. Мимикрия допускается только для
server-rendered или сторонних поверхностей, где React/shadcn неприменимы. Для них используется
общий **shared** admin UI kit, а Adminer сохраняет собственный изолированный CSS.

### 7.6. Встраивание сервисных админок

Стандартный способ композиции — same-origin iframe. Service admin frontend принадлежит своему
сервису и собирается отдельно; central Admin не импортирует его React-код.

Canonical URL shell:

```text
/admin?service=email#/templates/123
```

Защищённый URL iframe:

```text
/admin/service/email/templates/123
```

Shell и iframe используют небольшой `postMessage` protocol:

- shell передаёт theme и service-relative navigation;
- iframe сообщает текущий service-relative path и loading state;
- обе стороны принимают сообщения только от `window.location.origin`;
- reload, back/forward и direct protected URL сохраняют понятное поведение.

Текущая реализация query + hash + frame bridge переносится и нейтрализуется. Route-native импорт
Email editor в central Admin, full-page navigation вместо shell и module federation не используются.

Обработчик каждого **iframe load** повторно передаёт тему и завершает loading state, но не отправляет
устаревший parent path. Навигация parent → iframe отправляется при изменении route state. Иначе
вложенная навигация iframe может быть случайно отменена старым hash из shell.

## 8. Frontend stack

Базовый стек шаблона:

- **Site** — React и **TanStack Start**, SSR включён;
- **App** — React, **TanStack Router** и Vite, обычный client-side SPA без SSR;
- **Admin** и React-админки сервисов — React, TanStack Router и Vite, SPA без SSR;
- admin UI — shadcn/ui и общие design tokens.

Site и App остаются отдельными сервисами и сборками. Использование одного router family не даёт
им права импортировать код друг друга.

Переход с текущего React Router на TanStack является намеренным. Из текущей админки переносятся
компоненты, layout, design tokens и iframe protocol, но не Router implementation.

## 9. Site

Site содержит landing, публичные информационные и legal-страницы, контактную страницу, метаданные,
favicon, robots.txt, sitemap и 404. Он рендерится на сервере, не имеет собственной БД и не содержит
пользовательское приложение.

Юридические страницы в шаблоне являются структурой с placeholders, а не готовыми юридическими
текстами.

Минимальная страница, которая только отвечает на **/** и доказывает маршрутизацию, не является
реализованным Site.

## 10. App

App является SPA под **/app/**. Публично без сессии доступны только регистрация, вход,
восстановление доступа, сброс пароля и подтверждение email. Dashboard, onboarding и настройки
доступны только авторизованному пользователю.

До отрисовки защищённого route App проверяет сессию через Auth. Anonymous direct/deep link
перенаправляется на вход без показа защищённого интерфейса. Безопасный внутренний return path
сохраняется, чтобы после входа вернуть пользователя на исходную страницу; внешний URL или
произвольный redirect в него передать нельзя. При истечении или отзыве сессии действует то же
правило.

В базовом App нет трёх дублирующих верхнеуровневых разделов **Profile**, **Settings** и
**Account**. Используется один защищённый раздел настроек с логическими секциями:

- продуктовый профиль и пользовательские предпочтения, которыми владеет Users;
- аккаунт, безопасность и управление сессией, которыми владеет Auth.

Onboarding остаётся отдельным защищённым flow, потому что имеет собственное состояние завершения.
Отдельный route профиля добавляется только в конкретном продукте, если профиль является
самостоятельной пользовательской поверхностью, а не ещё одной формой настроек.

App не имеет БД. Identity и session он получает через Auth, продуктовый профиль — через Users.
Внутренний формат session cookie приложению не известен.

Route guard нужен для корректного пользовательского flow, но не заменяет серверную защиту: Auth,
Users и другие сервисы проверяют сессию на каждом защищённом endpoint.

Минимальная страница, которая только отвечает под **/app/**, не является реализованным App.

## 11. Auth и Users

Auth отвечает за минимальную identity пользователя, способы входа, сессии, подтверждение email,
восстановление доступа и связанные security flows. Он не владеет продуктовым профилем или правами
администратора. Секретные токены сохраняются только в безопасном виде, а recovery flow не раскрывает
существование email.

Auth service admin содержит поиск и список identity с состоянием подтверждения email, блокировки и
активных сессий. Администратору с доступом к Auth доступны базовые операции:

- отправить пользователю обычную одноразовую ссылку восстановления пароля;
- повторно отправить ссылку подтверждения неподтверждённого email;
- отозвать все пользовательские сессии;
- owner может заблокировать или разблокировать вход пользователя.

Администратор не задаёт и не видит пароль или recovery token. Восстановление использует тот же
ограниченный по времени flow через Notifications и Email, что и пользовательский запрос. Блокировка
сразу отзывает сессии и активные auth tokens. Owner не может заблокировать собственную identity,
поэтому действие не может удалить последнюю работающую owner session.

Все Auth admin mutations проходят проверку admin context и CSRF, записываются в Auth audit и
действуют со следующего запроса. Операции над identity не переносятся в Users.

Users отвечает за продуктовый профиль, onboarding и пользовательские настройки. Он не хранит
пароли, OAuth identity, session или admin rights и связывает профиль с identity из Auth.

## 12. Notifications

Notifications принимает только известные типизированные события от сервисов, защищается от
повторной обработки и маршрутизирует события в Email. Он не хранит почтовые шаблоны и не читает БД
других сервисов.

Шаблон содержит базовые auth-события, необходимые для регистрации, подтверждения email,
восстановления доступа и уведомления об изменении email.

## 13. Email

Email отвечает за версии шаблонов, локализацию, публикацию, пользовательские ограничения доставки,
отправки, статусы провайдера и неизменяемую историю фактически отправленного содержимого. Runtime
отправляет только опубликованную версию шаблона.

### 13.1. Редактор

В Email service admin встраивается open-source **Maily**. Редактор работает self-hosted как часть
сборки сервиса; внешние CDN и hosted editor не используются.

Maily заменяет только editor layer существующего Email service. Не переписываются заново templates,
locales, versions, draft/publish flow, preview, test send, delivery, provider statuses, immutable
outbound snapshot и audit.

Редактор сохраняет исходный документ Maily, а при публикации сервер формирует и проверяет финальные
HTML и plain text. Preview открывается в sandboxed iframe. Поддерживаются готовые email-блоки,
переменные, повторяемые секции, условия, черновики, публикация, история версий и тестовая отправка.

Редактор нужен только для создания шаблона. Runtime-доставка использует сохранённый опубликованный
результат и не загружает Maily.

Maily живёт в отдельной service-local сборке Email и загружается только на editor route. Большой
editor bundle не является частью central Admin и runtime delivery.

В общем pnpm lockfile фиксируется одна проверенная dependency graph: **@maily-to/core 0.3.7**,
**@maily-to/render 0.2.3** и единая линейка **TipTap 2.27.2**. Все пакеты TipTap разрешаются в одну
версию; смешивание 2.11.5 и 2.27.2 запрещено. Обновляется весь набор одновременно после clean
install, production build, server render и browser smoke. Новый template сразу создаёт Maily
documents, поэтому миграция Unlayer JSON в состав шаблона не входит. Рядом с editor document
хранится version marker; переход marker выполняется отдельной Email migration, а не автоматически
при старте новой библиотеки.

Email валидирует разрешённые variables/conditions/repeat data, sanitizes опубликованный HTML и
контролирует image upload/storage. Seed templates сразу создаются в Maily format.

### 13.2. Transport

Локально письма записываются в log и наружу не отправляются. Единственный готовый production
transport шаблона — **UniSender Go**. Email использует небольшой transport interface, через который
конкретный проект при необходимости добавляет другой провайдер обычным изменением кода.

### 13.3. Журнал отправок

Email service admin содержит журнал фактических отправок с поиском и постраничным списком.
Открытие записи показывает неизменяемый snapshot именно отправленного письма: тему, полный HTML,
полный plain text, получателя, время, transport и известный статус провайдера.

HTML доступен одновременно как экранированный исходник и как preview в sandboxed iframe без
выполнения scripts и доступа к origin админки. Журнал читает только Email DB и доступен через ту же
Gateway-проверку grant на Email; содержимое писем не передаётся в central Admin bundle или другие
сервисы.

## 14. Adminer

Adminer входит в инфраструктуру шаблона и открывается только через **/admin/service/adminer/**.
Gateway разрешает его исключительно owner. Отдельный публичный порт в production не открывается.

Готовый нейтральный визуальный слой Adminer, wrapper, Dockerfile и стили находятся в
**docker/adminer/** и используются целиком. Он не перерисовывается и не генерируется заново;
меняется только техническая конфигурация проекта. Поведение light, dark и system сохраняется. Все
крупные поверхности, sticky-панели, таблицы, формы, hover-состояния и controls используют theme
tokens: в dark theme не остаются принудительно белые фоны или светлые градиенты. Изменения не
должны удалять DOM-преобразования wrapper, на которые опираются стили. Зафиксированная версия
Adminer проверяется на совместимость с включёнными wrapper и stylesheet.

Adminer реализуется настоящим container, а не React/HTML-макетом:

- base image фиксируется как **adminer:5.4.2-standalone**; обновление выполняется отдельной задачей
  вместе с wrapper/CSS и browser-проверкой;
- wrapper и полный stylesheet входят в image;
- wrapper подключается на уровне PostgreSQL server с пустым `db`, а доступные базы обнаруживает
  сам Adminer; hardcoded registry сервисов и названий баз в PHP отсутствует;
- Compose использует только внутренний **expose**, без **ports**;
- Gateway не включает Adminer в public service allowlist;
- owner-only проверка выполняется до proxy;
- Adminer отсутствует в assignable service grants;
- browser acceptance test открывает реальный Adminer через Gateway для owner и получает отказ для
  обычного admin.

Acceptance учитывает настоящее поведение Adminer: первый запрос может вернуть redirect и установить
собственную session cookie. HTTP-проверка использует cookie jar, а browser-проверка ждёт элемент
реального интерфейса после redirect, а не только существование iframe body.

## 15. Contracts и данные

**contracts/** содержит oRPC contracts и Zod runtime schemas, но не server implementation, SQL или
секреты провайдеров.

У каждого stateful service своя PostgreSQL database и свои versioned migrations. Сервис может
работать только со своей БД. Локальный bootstrap создаёт нужные БД, а каждый сервис сам применяет
свои миграции.

Startup **CREATE TABLE IF NOT EXISTS** не заменяет migration system. Проверка поднимает пустую БД,
применяет миграции с нуля, затем проверяет upgrade минимум между двумя версиями и запись применённых
версий. Повторный запуск не изменяет уже применённую схему.

Шаблон использует один базовый **DATABASE_URL**. Если конкретному deployment нужны разные
credentials или hosts, он может задать service-specific overrides.

## 16. Docker и worktrees

### 16.1. Production

В production наружу публикуется только Gateway. Остальные сервисы находятся во внутренней сети,
получают только необходимые env и не публикуют собственные host ports. PostgreSQL считается
внешним управляемым ресурсом deployment platform и в production Compose приложения не входит.

### 16.2. Local

Локальный PostgreSQL является отдельным контейнером-сервисом, но объявлен в общем local Compose и
поднимается вместе с проектом. Это даёт один понятный lifecycle и общую внутреннюю сеть.

Каждый worktree получает собственный Compose project, контейнер PostgreSQL, volume и свободные
локальные порты. Worktrees не используют одну общую БД.

Шаблон не фиксирует один общий subnet для всех копий и worktrees. Обычно сеть выделяет Docker; если
его address pools исчерпаны, bootstrap может создать уникальный worktree-specific network override.
Он не удаляет и не перенастраивает чужие Docker networks.

Worktree bootstrap является обязательной частью template:

- находит main checkout без hardcoded path;
- копирует его локальный env как основу и заменяет worktree-specific значения;
- выбирает свободные порты;
- создаёт отдельный local PostgreSQL;
- копирует локальные service databases из main checkout в БД worktree;
- сохраняет всю локальную конфигурацию только в игнорируемом **.env**.

Базы переносятся логическим dump/restore, а не копированием Docker volume. Копируется состояние
локальной разработки, а не production data. Повторный bootstrap не должен случайно затирать уже
изменённую БД worktree: обновление копии выполняется только явно.

## 17. Документация и директивы

Template repository содержит **DIRECTIVES.md**, ссылающийся на него **AGENTS.md**, архитектурную и
deployment-документацию, описание админских прав и подробные README сервисов.

Каждое правило в **DIRECTIVES.md** называется директивой. Файл написан по-русски и редактируется
только владельцем проекта. Если задача противоречит директиве, агент сообщает об этом владельцу.

Файл хранится как UTF-8 с **LF** и финальным переносом строки. Агент не переписывает, не сокращает и
не переформатирует его даже без изменения смысла. Перед завершением agent-задачи проверяется, что
**DIRECTIVES.md** байт-в-байт не изменился, если владелец явно не поручал редактировать сам файл.
Самоутверждения в отчёте без фактического diff/hash check недостаточно.

В этом repository [DIRECTIVES.md](DIRECTIVES.md) является действующим базовым файлом директив.
Владелец заполняет описание продукта и при необходимости изменяет директивы отдельным осознанным
изменением.

## 18. Проверки

Общие проверки проекта должны покрывать типы, тесты, production-сборку, lint, границы сервисов и
маршрутизацию. Точные названия команд определяются при реализации шаблона.

Проверка выполняется из чистого checkout с общим pnpm lockfile. Обязательны:

- frozen clean install;
- корневые typecheck, test, build и lint;
- запуск корневых проверок без внешнего временного package-manager wrapper;
- проверка service boundaries;
- проверка Docker Compose configuration;
- clean build service-targeted runtime images без локальных **dist** и **\*.tsbuildinfo**;
- реальные отдельные containers для Gateway, Admin, Auth, Email, Adminer и PostgreSQL;
- PostgreSQL integration tests без in-memory замены;
- fresh и upgrade paths versioned migrations;
- oRPC/Zod contract tests;
- headless browser smoke central Admin и service iframe;
- реальный Maily mount и публикация JSON в HTML/plain text;
- настоящий Adminer через Gateway;
- проверка, что наружу опубликован только Gateway и локально выбранные host ports;
- проверка worktree bootstrap и logical dump/restore без неявного перезаписывания существующей БД.

Acceptance и browser tests не изменяют постоянное состояние общей dev-базы. Они используют
изолированную временную БД либо полностью восстанавливают созданных администраторов, grants,
шаблоны и другие fixtures после выполнения. Проверка частичного набора grants не должна оставлять
обычный локальный аккаунт с урезанными правами. Если в local demo есть постоянный обычный
администратор, он получает все назначаемые service grants; Adminer в этот список всё равно не
входит.

Обязательные security cases:

- anonymous direct/deep link на dashboard, onboarding или настройки App перенаправляется на вход
  без показа защищённого интерфейса;
- авторизованный пользователь открывает защищённые App routes, а отзыв сессии закрывает их со
  следующей проверки;
- return path после входа принимает только безопасный внутренний App route;
- Auth admin recovery создаёт обычное одноразовое письмо и не раскрывает token администратору;
- отзыв сессий закрывает существующие user sessions, а блокировка запрещает новый login;
- только owner может блокировать identity, при этом owner не может заблокировать себя;
- неизвестный public service недоступен;
- anonymous и обычный пользователь не открывают админку;
- admin без grant не достигает service admin;
- admin с grant открывает разрешённый сервис;
- owner открывает все service admins и Adminer;
- обычный admin никогда не открывает Adminer;
- клиент не может подделать передаваемый сервису admin context;
- прямой URL не обходит права и sidebar.

Также проверяются первый owner, защита последнего owner, синхронизация темы, публикация почтового
шаблона, отправка через log transport и изоляция service databases.

Отдельно проверяются:

- два параллельных bootstrap request создают одного owner и одно bootstrap audit event;
- owner может передать роль второму owner, но последний активный owner не отключается;
- изменение или отзыв grant действует со следующего Gateway request;
- service ids Gateway и Admin shell согласованы;
- клиентские control headers всегда удаляются и заменяются Gateway;
- недоступность Auth/Admin возвращает fail-closed service-unavailable response;
- admin assets не обходят admin authorization;
- logout инвалидирует server-side session и очищает HttpOnly cookie;
- central Admin использует реальные checked-in shadcn components;
- Email editor не входит в central Admin bundle;
- Email delivery log показывает полный сохранённый HTML и plain text, а preview не получает
  script/origin privileges;
- production Admin и Email bundles открываются в Chromium без JavaScript runtime errors;
- nested iframe navigation не откатывается устаревшим shell hash;
- сжатые upstream assets проходят Gateway без stale encoding headers;
- реальный Adminer проходит redirect с собственной cookie;
- light, dark и system темы настоящего Adminer проверяются в browser на database overview,
  таблице и пагинации, а не только на первой странице; тест проверяет вычисленные цвета основных
  поверхностей и не ограничивается наличием `data-theme`;
- container Adminer не имеет public host port;
- **DIRECTIVES.md** не меняется агентом без прямого поручения владельца.

## 19. Критерии приёмки

Шаблон готов, когда:

1. новый repository создаётся простым копированием без генератора;
2. для запуска не требуется переименовывать исходники и packages;
3. **.env.example** и **DIRECTIVES.md** находятся в Git, а **.env** игнорируется;
4. local bootstrap сам выбирает порты, URL и изолированную БД;
5. Site работает с SSR, App и Admin — как SPA;
6. только Gateway опубликован наружу;
7. сервисы не импортируют соседние сервисы и не читают чужие БД;
8. публичные auth flows работают, а dashboard, onboarding и единый раздел настроек App закрыты
   user session;
9. первый зарегистрированный Auth user становится owner при первом открытии Admin;
10. owner управляет администраторами, а Gateway блокирует сервисы без доступа;
11. Admin shell использует TanStack Router, реальные shadcn source components и существующий
    query/hash iframe protocol;
12. Adminer является настоящим внутренним container, доступен только owner и использует готовые
    wrapper и stylesheet из **docker/adminer/**;
13. Email сохраняет version/publish/delivery lifecycle, использует self-hosted Maily и UniSender Go
    transport и показывает полный журнал фактических HTML/plain-text snapshots;
14. каждый worktree получает копию local main DB в собственном PostgreSQL;
15. versioned migrations проходят fresh install и upgrade;
16. frozen clean install, Compose, PostgreSQL, browser и все общие проверки проходят;
17. runtime images service-targeted и не содержат весь monorepo;
18. локальные опубликованные порты по умолчанию слушают только loopback;
19. logout инвалидирует сессию на сервере, а не только удаляет cookie в браузере;
20. в template repository нет standalone npm lockfiles внутри сервисов;
21. в template repository нет секретов, production data, готовых legal-текстов и бренда исходного
    проекта;
22. Auth admin выполняет recovery, verification, session revoke и owner-only блокировку, а Email
    admin открывает полное содержание фактически отправленных писем.
